KEY DESIGN DECISIONS
================================================================================

1. MODULAR DOMAIN SCOPES
   Why: Phase 4+ domains (Marketing, Strategy, HR, Inventory) plug in as config
   changes, not prompt rewrites. No rewriting of [TAX_SCOPE] when adding
   [MARKETING_SCOPE].

2. SERVER-SIDE ASSEMBLY ONLY
   Why: Prevents client-side prompt injection, centralizes versioning control,
   makes A/B testing easier (change config, not frontend).

3. POST-PROCESSING GUARANTEES
   Why: BIR disclaimers, injection defense, and hallucination checks run AFTER
   Claude responds. Makes them reliable regardless of prompt changes.

4. DOMAIN TAGGING IN CONVERSATION HISTORY
   Why: Enables demand signal analytics. When users ask about things outside
   scope (e.g., "help me with Instagram"), we log it as "marketing" redirect.
   This data informs which domains to build next.

5. REGRESSION TEST LIBRARY AS HARD GATE
   Why: Prompt changes must be tested before shipping. Design gate prevents
   accumulation of quality drift over time.

6. CONFIDENCE SCORING IN OCR
   Why: Users need to know which fields are uncertain. Transparency over perfection.

7. THREE-LAYER INJECTION DEFENSE
   Why: No single layer is sufficient. Hardened prompt prevents most attacks, but
   sanitization and output filtering catch edge cases.
