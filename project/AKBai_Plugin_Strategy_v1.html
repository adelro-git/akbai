Executive Summary
Why one plugin, what it replaces, and how it's designed for your constraints.

The Problem

You're a solo founder building a full-stack AI product (Next.js PWA + Supabase + Claude API + Xendit) while working a day job at Globe. Your roadmap spans legal clearance, demand validation, MVP development across 5 pillars, payment integration, NPC compliance, and post-launch operations. That's the work of a 6–8 person team compressed into one person's spare time.

You already have Claude as your AI partner, but each session starts from scratch. There's no persistent memory of your architecture decisions, no consistent quality gates, no "team" that remembers your codebase patterns. Every conversation burns tokens re-establishing context.

The Solution: One Plugin, Many Roles

A single "akbai-delivery" plugin that bundles every function you need for end-to-end project delivery. Instead of installing separate plugins for engineering, design, marketing, and project management, this plugin encodes your specific project context — your tech stack, your architecture decisions, your Supabase schema, your brand voice, your BIR compliance requirements — into specialized skills and commands.

Key Design Decision

One plugin, not many. Token limits on Pro mean every skill description loaded into context costs you. A single plugin with 12–18 focused skills is more token-efficient than 4 separate plugins with overlapping descriptions. The tiyak-engineering plugin you already built proves this pattern works — we're extending it to cover the full delivery lifecycle.

Progressive Disclosure — The Token Budget Pattern

This is the most critical design choice for Pro plan efficiency. The plugin uses a three-tier loading system:

Tier 1 — Always in Context

~100 words per skill

Only the name and description from each SKILL.md frontmatter. This is what Claude sees in every conversation to decide which skill to activate. Total cost: ~1,200 words for 12 skills.

Tier 2 — On Trigger

~300–500 lines per skill

The SKILL.md body loads when Claude activates the skill. Contains role instructions, decision trees, and pointers to reference files. Only one skill loads at a time.

Tier 3 — On Demand

Unlimited reference files

Reference docs are only loaded when the skill explicitly reads them. The Supabase schema, for example, is only loaded when the data architect skill actually needs it.

Token Budget Reality Check

On Pro, you get roughly 25K–30K tokens of usable context per conversation after system prompts. Each skill description costs ~100 tokens. Loading a skill body costs ~2K–4K tokens. Loading a reference file costs ~1K–3K tokens. This architecture ensures you never load more than one skill + 1–2 reference files at a time. Maximum active context from the plugin: ~8K tokens, leaving 17K+ for your actual conversation and code.

Shared Context — The "Briefing Doc" Pattern

Instead of duplicating project context across 12 skills, a single shared/project-context.md file (~200 lines) contains the core information every skill might need: who AKBai is, the tech stack, current phase, and key constraints. Each skill's SKILL.md says "Read shared/project-context.md first if you haven't already" — but Claude only loads it once per conversation, not per skill activation.

Sub-Agent Strategy

On Pro, sub-agents (parallel task execution) have limits, but we can design for them strategically. Here's the approach:

Implemented via Skills

Single-focus roles

Most roles work as skills — they activate when triggered, load their context, do their job, and release. No persistent state needed. This is how all 12 core roles work.

Implemented via Sub-agents

Parallel review tasks

When you need multiple perspectives at once (e.g., code review + security review + test coverage check), sub-agents can run in parallel. Design commands like /review to optionally spawn parallel sub-agents for deeper analysis.

Token Efficiency Strategy
Pro plan means every token counts. Here's how we keep the plugin lean without sacrificing capability.

The Token Budget

What Costs Tokens

  • Skill descriptions — ~100 tokens each × 12 skills = ~1,200 tokens always in context
  • Skill body — ~2K–4K tokens when activated (one at a time)
  • Reference files — ~1K–3K tokens each (loaded on demand)
  • Shared context — ~1.5K tokens (loaded once per conversation)

What Doesn't Cost Tokens

  • Unactivated skills — Only their ~100-word description is in context
  • Unread reference files — Zero cost until explicitly loaded
  • Command files — Only loaded when the command is invoked
  • Scripts — Execute without loading into context

Seven Token-Saving Principles

1. One Role Per Conversation

Design skills so that most conversations only need one active role. The /build command chains multiple roles, but each role's body unloads before the next loads. In practice, a single conversation typically exercises 1–2 skills.

2. Condensed Reference Files

Your v8.0 roadmap is 20 pages. The roadmap-context.md reference file will be a ~200-line condensed version with only the information skills need: current phase, feature list, timeline, dependencies, and gap registry. Save the full document for human reading.

3. Deduplication via Shared References

Information that multiple skills need (tech stack, project context, glossary) lives in shared/ and is loaded once per conversation, not per skill activation. This eliminates the biggest source of duplication.

4. Smart Description Triggers

Skill descriptions are the most expensive always-on cost. Each description will be optimized using the skill-creator's description optimization loop to ensure high trigger accuracy with minimal words. Target: <80 words per description.

5. Command-First for Quick Tasks

Slash commands are cheaper than skill activations because they're single-purpose scripts. For routine tasks like standups, gap checks, and schema lookups, prefer commands over open-ended skill conversations.

6. Session Patterns — Start Fresh, Dive Deep

Design for short, focused sessions rather than long multi-topic conversations. A 20-minute "build the receipt scanner" session is more token-efficient than a 2-hour session that drifts across architecture, implementation, and marketing.

7. Reference Files as the "Brain" — SKILL.md as the "Guide"

Keep SKILL.md files under 300 lines. They should tell Claude how to think and when to load what. The actual knowledge (schemas, API specs, compliance checklists) lives in reference files that are only loaded when needed.

Open Questions & Decisions Needed
Before we start building, these questions need your input to finalize the approach.
Architecture

Q1: Single plugin vs. plugin + standalone skills?

The strategy above puts everything in one akbai-delivery plugin. An alternative is to keep your existing tiyak-engineer skill as a standalone and make the plugin cover everything except TIYAK-specific work. Since AKBai is a different project, the plugin should be self-contained. But if you ever want TIYAK skills to share context with AKBai skills (e.g., data quality patterns for AKBai's own data), we'd need to think about cross-plugin references.

Token Efficiency

Q2: How many skills descriptions can you tolerate in every conversation?

12 skills × ~100 tokens = ~1,200 tokens always loaded. If that feels too heavy, we can merge related roles (e.g., merge qa-engineer into fullstack-engineer, merge ops-lead into project-manager) to get down to 8–9 skills. The trade-off is less specialized behavior per role.

Project Context

Q3: Where does the codebase live?

The plugin's fullstack-engineer and data-architect skills need to know your project structure. Will the AKBai codebase be in a GitHub repo that Claude Code can access? Or will you primarily work in Cowork mode? This affects whether skills reference a /path/to/akbai/ root or use generic instructions.

Build Strategy

Q4: Build skills incrementally or scaffold all at once?

Option A: Build Phase A skills first, battle-test them during your actual Phase 0/1 work, then add Phase B/C skills based on what you actually need. Option B: Scaffold all 12 skills with basic SKILL.md files in one session, then iteratively improve each one. Option A is safer but slower. Option B gives you the full team faster but with less polish.

Existing Assets

Q5: Should we retire/replace the generic engineering and marketing plugins?

You currently have the generic engineering, design, and marketing plugins installed. Once the AKBai delivery plugin exists, those generic skills will overlap and compete for triggers. We should either uninstall them or design the AKBai plugin descriptions to win trigger priority over generic alternatives.

Persistence

Q6: Do you want the plugin to maintain state across sessions?

Skills can read/write to files in your workspace. This enables features like: a living sprint board (JSON file the PM skill updates), an architecture decision log (ADR Markdown files), or a gap registry tracker that persists progress. The trade-off is file management complexity. We could keep it simple with no persistent state and rely on GitHub issues/project boards instead.
